# 3. Архитектурный план

**Проект:** клиентское приложение картинг-центра «Апекс».
**Скоуп:** клиентское мобильное приложение + API к нему (R-028).

---

## 1. Контекст (C4 — уровень контекста)

```
        ┌──────────────┐     HTTPS/JSON    ┌────────────────────┐
        │   Клиент      │ ────────────────► │  API клиентского    │
        │ (мобильное    │ ◄──────────────── │  приложения (наш)   │
        │  приложение)  │                   └─────────┬──────────┘
        └──────────────┘                              │ контракт API
                                                       ▼
                                        ┌──────────────────────────┐
                                        │  Существующий бэкенд       │
                                        │  центра (BLACK-BOX):       │
                                        │  расписание, слоты,        │
                                        │  маршалы, атомарная бронь, │
                                        │  push, отмена центром      │
                                        └──────────────────────────┘
```

**Граница ответственности (R-004).** Транзакционность, «0 двойных броней», SLA,
маппинг на внутренние модели — на стороне существующего бэкенда. Наше приложение
общается с ним **только через контракт API** и корректно обрабатывает отказы.

> В учебном проекте реального бэкенда центра нет, поэтому наш API-сервер **исполняет
> роль этого контракта**: реализует те же гарантии (атомарная проверка мест) на
> in-memory хранилище. Это позволяет запустить и продемонстрировать все клиентские
> сценарии end-to-end, не выходя за границы контракта.

## 2. Компоненты (уровень контейнеров)

| Контейнер | Технологии | Ответственность |
|-----------|-----------|-----------------|
| **client** | React 18 + TypeScript + Vite | UI, мобильная вёрстка, экраны, вызовы API |
| **server** | Node.js + Express + TypeScript | Контракт API, бизнес-правила брони/отмены/оценки, атомарная проверка мест, сид расписания |

Разделение по слоям на сервере:

```
server/src/
  domain/        # сущности и бизнес-правила (чистая логика, тестируется юнитами)
    slots.ts       — фильтр 7 дней, скрытие прошедших
    booking.ts     — правила брони, отмены (порог 60 мин), оценки
  store/         # in-memory хранилище + сид расписания на 7 дней
  http/          # Express-роуты, маппинг ошибок домена → HTTP-коды
  app.ts         # сборка приложения (для тестов и dev)
  server.ts      # точка входа
```

Клиент по слоям:

```
client/src/
  api/           # типизированный клиент API (fetch)
  screens/       # экраны: список слотов, карточка, мои брони
  components/    # переиспользуемые UI-компоненты (карточка слота, звёзды и т.д.)
  types.ts       # общие типы контракта
```

## 3. Ключевые архитектурные решения

- **AD-1. In-memory хранилище вместо БД.** Проект учебный, исторических данных нет
  (R-015). Хранилище инкапсулировано за интерфейсом `store` — замена на БД не затронет
  доменный слой.
- **AD-2. Атомарность брони внутри обработчика.** Node однопоточен; проверка
  «есть свободный карт → декремент» выполняется **синхронно, без `await` между чтением
  и записью**, что гарантирует отсутствие двойных броней в рамках процесса (модель
  контракта R-004). При переходе на БД заменяется на атомарный `UPDATE ... WHERE
  free_karts > 0`.
- **AD-3. Производный статус `completed`.** Бронь считается завершённой, если её слот
  уже закончился и она не была отменена. Не храним отдельным полем — вычисляем при
  чтении, чтобы не заводить фоновый планировщик в MVP.
- **AD-4. Демо-авторизация.** Клиент идентифицируется заголовком `x-user-id`
  (по умолчанию — демо-клиент). Реальная авторизация по телефону — вне MVP (A-009),
  но контракт к ней готов.
- **AD-5. Симуляция действий внешней инфраструктуры.** Отмена слота центром (R-008)
  и завершение заезда — действия внешнего бэкенда (вне скоупа клиента). Для демонстрации
  добавлены служебные `/api/dev/*` эндпоинты, **явно помеченные как симуляция** и не
  входящие в клиентский контракт.

## 4. Обработка ошибок (контракт клиент↔сервер)

Доменные ошибки маппятся на HTTP-коды и единый формат тела:

```json
{ "error": { "code": "NO_SEATS", "message": "Мест уже нет" } }
```

| Код домена | HTTP | Когда |
|------------|------|-------|
| `NO_SEATS` | 409 | нет свободных картов при записи (гонка) |
| `ALREADY_BOOKED` | 409 | клиент уже записан на слот |
| `RENT_UNAVAILABLE` | 400 | выбран прокат, но фонд исчерпан |
| `SLOT_NOT_BOOKABLE` | 409 | слот отменён центром / уже прошёл |
| `LATE_CANCEL` | 409 | отмена ≤ 60 мин до старта |
| `NOT_CANCELLABLE` | 409 | бронь не в статусе «подтверждена» |
| `NOT_COMPLETED` | 409 | оценка до завершения заезда |
| `ALREADY_RATED` | 409 | повторная оценка |
| `INVALID_RATING` | 400 | звёзды вне диапазона 1–5 |
| `NOT_FOUND` | 404 | нет слота/брони |

## 5. Нефункциональные требования (MVP)

- **Платформа:** мобильный веб, макет ~390px (основное устройство — телефон).
- **Локаль:** ru-RU, время — локальное; даты в API — ISO-8601 (UTC).
- **Устойчивость:** клиент обрабатывает все коды ошибок из §4 понятными сообщениями.
- **Тестируемость:** доменный слой покрыт юнит-тестами, контракт API — интеграционными.
