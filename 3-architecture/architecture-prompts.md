# Промпты — этап архитектуры

**Инструмент:** Claude Code · модель **Claude Opus 4.8**.

---

### Промпт 1 — архитектурный план

```
Спроектируй архитектуру клиентского приложения картинг-центра (роль Клиент) + API к
нему. Учти границу R-004: реальный бэкенд — black-box, гарантирует атомарность и «0
двойных броней»; наш API исполняет роль контракта. Опиши: контекст (C4), контейнеры
(client/server), слои сервера (domain/store/http), ключевые архитектурные решения с
обоснованием, обработку ошибок (маппинг доменных ошибок на HTTP-коды), НФТ.
```

### Промпт 2 — схема данных

```
Спроектируй схему данных как контракт API (R-015): сущности Marshal, Slot, Booking,
Rating, User; ER-диаграмма, поля с типами, инварианты (лимит 8 для короткой трассы,
0<=freeKarts<=totalKarts), бизнес-правила на данных. Статус completed — производный,
не хранимый.
```

### Промпт 3 — контракт эндпоинтов

```
Опиши REST-контракт: GET /slots (фильтр from/to, дефолт 7 дней, скрытие прошедших),
GET /slots/:id, GET /bookings, POST /bookings (атомарная бронь), POST
/bookings/:id/cancel (порог 60 мин), POST /bookings/:id/rating. Для каждого — тело
запроса/ответа и таблицу ошибок с HTTP-кодами. Отдельно — dev-эндпоинты для симуляции
отмены центром (R-008), явно пометив их как вне клиентского контракта.
```

### Промпт 4 — атомарность брони

```
Как гарантировать отсутствие двойных броней на in-memory хранилище в Node? Объясни,
почему синхронная проверка «freeKarts>0 → декремент» без await атомарна в однопоточном
процессе, и как это заменится на атомарный UPDATE ... WHERE free_karts>0 при переходе
на БД.
```
