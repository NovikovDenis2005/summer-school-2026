# 1. Выявление требований — уточняющие вопросы к заказчику

**Проект:** клиентское приложение картинг-центра «Апекс»
**Заказчик:** Денис (владелец)
**Роль:** аналитик
**Вход:** [0-brief/brief-karting.md](../0-brief/brief-karting.md)

Бриф намеренно неполный и местами противоречивый. Ниже — вопросы, сгруппированные
по темам. Для каждого указан **источник пробела** в брифе, **вопрос** и
**принятое решение** (часть закрыта уточнениями к брифу — маркеры `R-004 … R-028`,
часть — задокументированные допущения аналитика, помеченные `[ДОПУЩЕНИЕ]`).

Полный список решений в машиночитаемом виде — [decisions.md](decisions.md).
Отправленные ИИ-промпты — [elicitation-prompts.md](elicitation-prompts.md).

---

## Тема A. Границы скоупа

**A1. Что именно мы делаем — всё приложение или часть?**
Пробел: в письме Денис просит «нормальное приложение», но инфраструктура уже есть.
→ **Решение (R-028):** делаем **только клиентское мобильное приложение + API к нему**,
роль **Клиент**. Интерфейсы маршала и владельца/админки — вне скоупа.

**A2. Кто создаёт слоты и расписание?**
Пробел: в письме владелец «правит расписание руками».
→ **Решение (R-004, R-028):** расписание, слоты, конфигурации трасс и маршалы
приходят из существующего бэкенда через API. Клиент их **только потребляет**.

**A3. Кто гарантирует отсутствие двойных броней?**
Пробел: главная боль заказчика — «записываю двоих на один карт».
→ **Решение (R-004):** атомарная проверка свободных картов — на стороне бэкенда
(black-box). Клиент полагается на ответ API и корректно обрабатывает отказ
«мест нет».

---

## Тема B. Слоты и запись

**B1. На какой период показывать слоты по умолчанию?**
Пробел: «расписание на неделю вперёд», но не сказано, что видит клиент.
→ **Решение (R-027):** по умолчанию — **ближайшие 7 дней**. Более длинный период —
через фильтр дат. Нет расписания → empty state «Пока нет доступных заездов».

**B2. Какие бывают конфигурации трассы и лимиты?**
Пробел: «короткая для новичков», «длинная для опытных», «картов 14, но на
новичковые больше 8 не ставим».
→ **Решение:** две конфигурации:
- `short` (новичковая) — лимит **8** мест, часть картов с ограничением скорости;
- `long` (для опытных) — до **14** мест.
Вместимость конкретного слота (`totalKarts`, `freeKarts`) приходит из API —
клиент её не вычисляет. `[ДОПУЩЕНИЕ]` соответствие «short ↔ новичковая» фиксируем.

**B3. Экипировка: своя или прокат — как влияет на запись?**
Пробел: «выбирал, со своей экипировкой он или ему дать напрокат».
→ **Решение (R-015):** при бронировании клиент выбирает `own` / `rent`.
Прокатный тариф и свободный прокатный фонд отдаёт бэкенд в контракте API.
`[ДОПУЩЕНИЕ]` если фонд проката исчерпан — вариант `rent` недоступен, `own` доступен.

**B4. Нужна ли онлайн-оплата на старте?**
Пробел: «хотелось бы сразу, но принимаю наличкой и переводом… не уверен, потянем ли».
→ **Решение `[ДОПУЩЕНИЕ]`:** онлайн-оплата **вне MVP**. В брони фиксируем стоимость
(`priceRub`), оплата — на месте (наличные/перевод). Заложить поле статуса оплаты
на будущее, но UI оплаты не делаем.

## Тема C. Отмена

**C1. Правило отмены брони клиентом — где граница «поздней» отмены?**
Пробел (противоречие): «если заранее — ок… если за 10 минут — проблема… ограничить,
но клиентов не злить». Точная граница не задана.
→ **Решение `[ДОПУЩЕНИЕ, подлежит подтверждению у Дениса]`:**
- отмена **бесплатна и свободна**, если до старта **> 60 минут**;
- если до старта **≤ 60 минут** — отмена **через приложение запрещена**, показываем
  понятное сообщение «Поздняя отмена невозможна, свяжитесь с центром» + телефон.
Такой порог защищает от простоя карта, но не блокирует всё подряд. Точное значение
(60 мин / 2 часа) — согласовать с заказчиком.

**C2. Отмена заезда самим центром (погода/форс-мажор) — что видит клиент?**
Пробел: «в дождь/гололёд отменяем целиком, надо всех разом предупредить».
→ **Решение (R-008):** при отмене центром бронь **не удаляется**, а получает статус
**«Отменён центром»** с причиной; клиенту приходит **push**. Повторная запись на
отменённый слот **запрещена**. Само действие отмены — в инфраструктуре, вне скоупа.

## Тема D. Оценки маршалов

**D1. Кто, когда и как ставит оценку?**
Пробел: «после заезда клиент мог поставить оценку маршалу».
→ **Решение `[ДОПУЩЕНИЕ]`:**
- оценку ставит клиент **только по завершённому** заезду (`status = completed`);
- шкала **1–5 звёзд** + необязательный комментарий;
- одна оценка на бронь, редактирование — вне MVP;
- средний рейтинг маршала приходит из API (`ratingAvg`, `ratingCount`).

---

## Тема E. Уведомления и лояльность

**E1. Напоминания о записи — в MVP?**
Пробел: «может, какие-то уведомления… а то забывают».
→ **Решение `[ДОПУЩЕНИЕ]`:** напоминания-пуши о предстоящем заезде — **вне MVP**
(бэклог). В MVP обязателен только push об **отмене центром** (R-008).

**E2. Программа лояльности для постоянных клиентов?**
Пробел: «было бы здорово их отмечать / давать приятное».
→ **Решение `[ДОПУЩЕНИЕ]`:** **вне MVP**. Заложить флаг `isRegular` в модель клиента
для будущего, без механики бонусов.

**E3. Учёт погоды на трассе?**
Пробел: «хорошо бы погоду учитывать».
→ **Решение `[ДОПУЩЕНИЕ]`:** отдельной интеграции с погодой в клиенте нет; решение
об отмене по погоде принимает центр, клиент видит результат через C2/R-008.

---

## Тема F. Идентификация клиента

**F1. Как клиент авторизуется?**
Пробел: в письме не описано.
→ **Решение `[ДОПУЩЕНИЕ]`:** полноценная регистрация/OTP — вне текущей поставки.
Для демо MVP используется **преднастроенный демо-клиент** (роль Клиент). Модель и
API спроектированы так, чтобы позже подключить реальную авторизацию по телефону.

## Открытые вопросы к следующей итерации с заказчиком

1. Подтвердить порог «поздней отмены» (C1): 60 мин или 2 часа?
2. Нужна ли клиенту история прошлых заездов (архив), помимо предстоящих?
3. Формат push: только отмена центром или ещё и напоминания (E1)?
4. Нужен ли выбор конкретного маршала при записи, или только просмотр его рейтинга?
